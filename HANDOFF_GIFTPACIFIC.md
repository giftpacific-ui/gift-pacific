## P3 — Tracking: Meta Pixel + Conversions API, GA4/GTM, attribution, consent (implemented; NOT type-checked in full / built / run against a database or Meta/Google)

### What was found (existing system, extended not rebuilt)
`src/lib/analytics/*` already loaded GTM/GA4, Meta Pixel, TikTok and LinkedIn behind an `OFF` / `OPT_IN` consent mode, and `submitCheckout` sent a server Purchase. Defects fixed:
1. **Purchase fired on order creation** (server CAPI in `submitCheckout` AND browser on the confirmation page), whatever the order status.
2. **GA4 direct mode (`G-…`) never received ecommerce events**: they were plain-object `dataLayer` pushes, which gtag.js ignores (only GTM reads them). Not verified live; confirm in GA4 DebugView.
3. `pushToDataLayer` had **no consent check**: events pushed before consent would be replayed by GTM once it loaded.
4. Graph API **`v20.0` hard-coded** (published deprecation 2026-09-24).
5. `AddPaymentInfo` fired on page load with no items/value; `InitiateCheckout` omitted quantities; the order confirmation sent no items/tax/shipping/coupon.
6. Server events under `OPT_IN` were never sent (the server could not see consent).

### Purchase trigger policy (chosen from the existing workflow, not invented)
A website order's Purchase is generated when the order **enters `CONFIRMED` through `adminUpdateOrderStatus`** (admin action or courier sync). `PENDING→CONFIRMED` is the only way into `CONFIRMED`, and that function already refuses to confirm an order whose required advance is not VERIFIED/waived or whose low-trust review is open. COD and prepaid follow the same rule. It does not wait for delivery.
- Never a Purchase: PENDING orders; non-website channels (marketplace/external, which bypass checkout); orders CANCELLED / REFUND_REQUESTED / REFUNDED / FAILED_DELIVERY at delivery time (a waiting event is SKIPPED).
- An already-accepted Purchase is **not reversed** if the order is later cancelled (no standard "un-purchase" event); the audit row shows what was sent.
- Exactly once: unique `(destination, eventName, orderId)` row + `createMany skipDuplicates`; event id `purchase_<orderNumber>` (`ids.ts`, single definition) is shared by browser and server so Meta de-duplicates.
- Browser Purchase (Meta Pixel, and GA4 only when the server does not own GA4 - see P3.1) fires only if the order is **already confirmed when the customer views the confirmation page** (`purchaseEligibility`); once per order per browser.

### Attribution

## P3.1 — GA4 Measurement Protocol purchase, consent withdrawal, background delivery (implemented; same BLOCKED checks as P3)

### Delivery policy (one reliable sender per destination)
| Destination | Sender | Notes |
|---|---|---|
| **GA4 `purchase`** | **Server only** (Measurement Protocol) when `GA4_API_SECRET` is set; the storefront then **omits** the browser GA4 purchase (`serverSendsGa4` → `purchaseEvent(..., {includeGa4:false})`). If the secret is not set, the browser sends it as in P3 (only when the order is already confirmed at page view). | Google's docs describe **no** de-duplication between browser and Measurement Protocol events, so exactly one sender is the only safe policy. In validation mode (`GA4_MP_DEBUG`) nothing is recorded, so the browser keeps sending. |
| **Meta `Purchase`** | Browser Pixel (if already confirmed at page view) **and** server CAPI, de-duplicated by the shared event id `purchase_<orderNumber>`. | unchanged from P3 |
Trigger (unchanged): the order **enters `CONFIRMED`** through `adminUpdateOrderStatus`. One `TrackingEventLog` row per (destination, event, order): destinations `META_CAPI` and `GA4_MP` (the `destination` column was already free text; no enum change).
GA4 specifics (from Google's docs, verified): endpoint `https://www.google-analytics.com/mp/collect?measurement_id=…&api_secret=…` (the **secret is in the URL query by Google's design** - it is redacted from every message/log/stored error and never reaches the browser); `client_id` is required; events may be back-dated at most **72 h** and older ones are *accepted but silently re-dated*, so events older than **71 h are skipped** (`event_too_old`) instead of sent. Payload params come from the **same `purchaseEvent()` as the browser** (transaction_id, currency BDT, `value` = total − shipping − tax, tax, shipping, coupon, items) plus `session_id` (when captured) and `engagement_time_msec:1`; `timestamp_micros` = confirmation time.
**Client id**: read at checkout from the first-party `_ga` cookie (`GA1.x.<random>.<ts>` → `<random>.<ts>`), session from `_ga_<MEASUREMENT>`; both strictly validated, stored on the existing `OrderAttribution` row, **only when consent permits and GA4 server purchase is configured**. No client id ⇒ GA4 event `SKIPPED no_client_id` (never invented; Meta unaffected). Visitors whose browser never ran GA (blocked/no consent) therefore produce no GA4 purchase, consistent with GA4 never having seen them.
Identifiers (IP, user agent, GA client/session id) are erased once **no event of the order can still be delivered** (all SENT/SKIPPED; a **FAILED** event keeps them for an admin retry until the 8-day cleanup - found and fixed during testing), or immediately on consent withdrawal.

### Background delivery architecture (replaces the 6-second wait)
`adminUpdateOrderStatus` (after commit) → `trackOrderConfirmed`: **persists** the PENDING rows (a few fast DB writes) and schedules `after()` (Next's post-response hook) to deliver them; it never waits for Meta/Google. `after()` is only an optimisation: the **guaranteed** mechanisms are (1) the persisted PENDING row and (2) the retry job `POST /api/tracking/retry` (`Authorization: Bearer $CRON_SECRET`; also "Run delivery job now" in admin), which delivers due rows, **recovers crashed workers** (stale `SENDING` claims after 2 min), **back-fills** confirmed orders whose rows were never persisted (from the order's CONFIRMED history row, ≤7 days), re-queues rows skipped as `not_configured` once configured, and erases old identifiers. Idempotency is unchanged (unique row per destination+order, guarded claim). **Without a scheduler** only the single post-response attempt runs, so schedule the job (diagnostics warns when events wait and `CRON_SECRET` is missing).

### Consent withdrawal (fixes the P3 limitation)
- On **grant**, the browser mints an opaque reference (`gp_cref` cookie): 128 random bits from `crypto.getRandomValues`, **not derived from email/phone/order/user data**. Checkout stores it on `OrderAttribution.consentRef` (only when consent permits).
- On **withdrawal** (granted → denied) the browser clears tracking cookies (`_fbp,_fbc,_ga*,_gcl_*,_tt*,gp_attr,gp_cref`) and calls `POST /api/consent/withdraw {ref}` (`fetch` with `keepalive`). A **pending marker** is stored before the request and cleared only on a 2xx, and retried on every page load (offline / reload / 500). A first-time "decline" makes no request.
- Server (`withdrawTrackingConsent`): finds the affected orders by **the reference and/or the signed-in customer's account** (covers guests, and customers withdrawing from another device), then (a) turns every **PENDING / FAILED** event into `SKIPPED consent_withdrawn` (the retry job and the admin Retry cannot send it), (b) marks the attribution `DENIED` + `consentWithdrawnAt` and **erases** touches, fbc/fbp, IP, user agent, GA ids and the reference. It reads/writes **no order, payment or customer record**; orders are never deleted. A delivery that is being prepared re-checks consent **immediately before the request**, so a withdrawal arriving mid-preparation still wins.
- The endpoint is same-origin only (403 otherwise), rate limited (existing limiter, generous), accepts ≤512 bytes, validates the reference (400), answers only `{ok:true}` whether or not anything matched (no order ids, no counts, no probing), and answers 500 on a server error so the browser retries.
- **Already-delivered events (SENT) stay SENT and are NOT recalled**: neither the Meta Conversions API nor the GA4 Measurement Protocol offers per-event deletion, and this code does not claim otherwise. Withdrawal after delivery erases our stored identifiers and prevents any further event; data already at Meta/Google follows their own retention/deletion tools (a deletion request there is a manual process).
- Limits: consent is per browser. A signed-in customer's withdrawal applies to all **existing** orders on their account; an order later placed from another browser carries that browser's own consent. Orders placed before P3.1 (or by visitors who granted before it) have no reference, so a guest withdrawal cannot find them (signed-in customers are still covered by account). A request that raced ahead of the order snapshot insert is not covered (the consent cookie is already `denied` for any later request).

Server-side today: **Purchase** (Meta + GA4). **Browser-only:** PageView, ViewContent, Search, AddToCart, RemoveFromCart, InitiateCheckout, AddPaymentInfo, AddToWishlist, Lead, CompleteRegistration. No second pipeline was built. **Safe future approach** for server ViewContent / AddToCart / InitiateCheckout: (1) the browser already generates a per-occurrence `eventId` for every event (`newEventId`) and passes it to `fbq(..., {eventID})`; relay the **same id** to a same-origin endpoint so Meta de-duplicates browser+server by `event_id`+`event_name`; (2) the endpoint accepts only `{eventName, eventId, productId(s), quantity}`, **re-derives price/currency/name from the catalogue** (never trusts client values), and rate-limits; (3) consent: require `gp_consent=granted` (OPT_IN) at request time and reuse the `gp_cref` reference so a withdrawal also drops queued relays; (4) user data only from first-party cookies already used here (`_fbp/_fbc`, IP, UA - raw as Meta requires) with email/phone only for logged-in checkout events, hashed as in `server-events.ts`; (5) persist via the same `TrackingEventLog` + retry job with a new `eventName`, keeping one lifecycle. ## P4 — Fraud prevention, customer risk analysis & order protection (implemented; NOT type-checked in full / built / run against a database)

### Architecture (what was reused, what is new)
**Reused, unchanged in meaning:** the advance-payment verification and the low-trust review (`advance-policy.ts`, `advance.service.ts`); the courier-evidence **trust score** (higher = safer, still decided once at checkout and never recomputed); the **single gate** `dispatchBlockedReason()` (used by the status funnel and courier booking); `assertAdminActor` / `recordAudit` / `AdminAuditEvent`; the PostgreSQL rate limiter; the `normalizeBdPhone` normaliser; the cart-claim guard in `placeOrder`; the P3/P3.1 tracking lifecycle.
**New:** a separate **risk score** (higher = riskier, 0-100) built only from internal evidence, which *consumes* the stored trust result as one signal and never alters it.
- `lib/fraud/` (pure, unit-tested): `identity.ts` (phone/e-mail/IP/address normalisation), `policy.ts` (levels, defaults, validation), `scoring.ts` (deterministic scoring + explanation + the gate function), `customer-stats.ts`.
- `server/services/`: `fraud-evidence.service` (reads real records, bounded queries), `fraud-risk.service` (policy, evaluate, persist, retention), `fraud-review.service` (approve/reject/override, order-page data), `risk-list.service`, `customer-risk.service`, `fraud-report.service`, `checkout-guard.service` + `checkout-flow.service` (idempotency, rate limits, block-reject; extracted from the `"use server"` action so it is testable).
- Admin: `/admin/fraud` (queue), `/admin/fraud/customers`, `/lists`, `/reports`, `/settings`, a **Fraud risk card on the order page**, nav entry; actions in `server/actions/admin-fraud.actions.ts`; job `POST /api/fraud/maintenance` (bearer `CRON_SECRET`).

### Risk score: explainable and configurable
Score = sum of signals, clamped 0-100. Every point appears as a signal (label, **reason with the real numbers**, exact points, related order numbers) or an explicit adjustment, and the parts reconcile exactly with the total. Each assessment stores its signals, the **frozen policy** it used, the evidence counts and the **calculation time**; identical re-evaluations only refresh `riskAssessedAt` (no duplicate rows), so the history is the real score history.
Default levels (configurable): **LOW 0-29, MEDIUM 30-59, HIGH 60-79, CRITICAL 80-100.**
| Signal (verifiable data) | Default points |
|---|---|
| Earlier cancelled orders (same phone/e-mail/account; excludes fraud rejections) | 8 each, max 24 |
| Earlier failed deliveries (ever had a FAILED_DELIVERY event) | 15 each, max 45 |
| Earlier orders rejected in fraud review | 25 each, max 50 |
| Earlier advance payments rejected by staff (Payment FAILED) | 10 each, max 20 |
| Many orders from this phone in 24 h (first 1 free) | 6 each, max 24 |
| Identical cart (same items+quantities) within 30 min | 15 each, max 30 |
| Same address used with ≥3 other phones in 7 days (weak: households/gifts) | 8 |
| Same e-mail used with ≥2 other phones in 30 days | 12 |
| ≥5 different phones from one IP in 24 h (weak: shared networks; needs an IP) | 6 |
| Address/name looks like a placeholder (text only; Bangla-safe) | 10 |
| Existing zone-mismatch flag / poor courier trust evidence (stored values; "no evidence" is NOT penalised) | 8 / 20 |
| High-value first order (≥ 15 000 BDT, no delivered history) | 10 |
| Block list: phone / e-mail / IP | 100 / 100 / 60 (and a **floor**: phone/e-mail ⇒ at least CRITICAL, IP ⇒ at least HIGH whatever the weights) |
| Credits: allow-list phone / e-mail / IP, delivered earlier to same address by same phone, staff-verified advance | -30 / -30 / -10, -12, -8 (total credit capped at 40; **none applied beside a block**) |
Shared IPs are never treated as one customer; with no IP nothing is inferred. These weights are **starting values, not calibrated on your data**: review the first weeks of reports and adjust in Settings. Thresholds, weights, windows, counts, high-value amount, credit cap, retention and mode are validated (e.g. medium < high < critical; invalid or overlapping settings are refused on save, and an invalid *stored* policy falls back to the defaults, never to something weaker). Changes are audited with before/after.

### Order confirmation policy
Mode (Settings): **ENFORCE** (default) / ADVISORY (score + warn, never block) / OFF (no evaluation).
| Level | Behaviour (ENFORCE) |
|---|---|
| LOW | normal workflow |
| MEDIUM | warning card for admins; normal manual confirmation |
| HIGH | order cannot be confirmed/dispatched until an admin records a **review with a reason (≥10 chars)** |
| CRITICAL | held for manual review; same recorded review, restricted to the **designated reviewers** if any are set (the project has only `ADMIN`/`CUSTOMER` roles, so this list is the finer permission; empty = any active admin). A refused attempt is audited. |
Enforcement point: the existing single gate, evaluated **after** the advance check and the low-trust review (a fraud approval can never satisfy or replace either, and neither can satisfy it). A pending website order is **re-evaluated at the moment an admin tries to confirm it** (so a block added after checkout or new activity is seen); if evaluation fails and the order was never assessed, confirmation is refused (fail closed). **Approve** lifts only the fraud hold up to the level reviewed (if risk later escalates, e.g. a block is added, the order is held again); it does not confirm and cannot verify an advance. **Reject** cancels through the normal status funnel (reason recorded; if the cancel fails the rejection record is undone). The decision is bound to the assessment the admin viewed (stale ⇒ refused). Recalculation may also de-escalate when evidence changes (e.g. an admin allow-listed the customer); every assessment is kept. Nothing cancels an order automatically. Marketplace/external orders are never scored. **P3/P3.1:** a held, rejected or unconfirmed order creates no Purchase event (tested end-to-end).

### Duplicate / repeated orders, concurrency, rate limits
- **Idempotency:** the browser sends one random `checkoutKey` per checkout attempt; `Order.checkoutKey` is UNIQUE. Replays (double click, retry after a lost response, concurrent requests) return the first order's result and never create a second; a different customer/phone/old key is refused; two real orders (different keys) are never merged; a failed attempt does not burn the key. The existing cart-claim in `placeOrder` remains the first line of defence.
- **Signals (never auto-cancel):** frequency per phone and identical-cart duplicates raise the score so an admin decides.
- **Rate limits** (existing limiter): checkout **6 / 10 min per phone** (tight) and **20 / 10 min per IP** (generous; skipped when no IP is known); replays are not counted.

### Block / allow lists
Phone, e-mail, IP; matching on the **normalised** value (any Bangladesh phone spelling, Gmail dots/+tags, IPv6 /64); **exact only** (no ranges). Reason mandatory (≥5), admin + timestamp recorded, optional expiry (ignored automatically once past), disable with reason, entries never deleted, every change audited, nothing is ever added automatically. **IP blocks must expire (≤90 days)** and only send an order for review. Default action for a blocked phone/e-mail is **HOLD** (accept and force manual review); the admin may choose **REJECT** at checkout (generic message that reveals nothing; never for IP blocks, only in ENFORCE). An allow entry only lowers the score: it cannot offset a block and never touches advance verification or the low-trust review.

### Customer profile (admin-only)
By normalised phone, e-mail or account (guests included), built from real orders: total / confirmed / delivered / cancelled / failed deliveries, cancellation rate (cancelled ÷ total), failed-delivery rate (failed ÷ (delivered+failed)), successful purchase value (currently DELIVERED, refunds excluded), fraud rejections, high/critical counts, admin overrides, current risk, score history, recurring signals, active list entries, recent orders. **Refused COD is not recorded by the system and is shown as such** (failed delivery is the nearest outcome). Another customer's data never appears (tested); customers can never see any of it (every new column is on `ORDER_INTERNAL_FIELDS`; static guard forbids customer-facing code from importing fraud services).

### Reports (real data, bounded queries)
Orders by level, high/critical trend per day, repeat cancellations, failed-delivery patterns, repeated phone/e-mail/IP activity (masked), review outcomes, **overrides and how they turned out** (delivered share = closest recorded sign of a false positive; not proof). Scans are capped at 5 000 rows per query and the page says when a period was truncated; empty data shows zeros.

### Security & privacy
Server-side validation everywhere; scores/levels/decisions can only be set by the server (a forged client submission is ignored: tested); every fraud page and action calls `requireAdmin()` (static guard) and services re-check an **active** admin; audit events for policy changes, list changes, recalculations, approvals, rejections, refused reviews. Stored personal data: normalised phone/e-mail keys and an address **hash** on the order (admin-only, needed for matching); the visitor's **IP only on the assessment**, erased after `ipRetentionDays` (default 30) by the maintenance job (scores and reasons stay). **No browser/device fingerprinting was implemented**: it is invasive and legally sensitive (consent/ePrivacy), and the evidence it adds is weak next to the verified signals above; a first-party random device cookie would be the safer future option and needs a privacy-policy decision.

## P5 — Courier integration, booking automation, shipment status sync, COD reconciliation (implemented; NOT type-checked in full / built / run against a database or the live courier)

### Read this first: two defects found in the existing courier code and fixed
1. **Booking ignored the verified advance.** `bookOrderWithCourier` never selected `advancePaid`, so the COD amount sent to Steadfast was computed as if no advance had been paid: a customer who had paid a verified advance would have been asked for the full total at the door. Fixed (`bookingSelect` now includes it). The fake DB ignores `select`, so this is guarded by a static test (`STATIC GUARD`) + a behavioural test; only a real-DB run proves it end to end.

An ADMIN marking an order delivered is unchanged (still records COD). Courier-delivered COD orders now sit as "Delivered: collection to be confirmed" until staff use **Confirm cash collected** (`confirmCodCollection`, reason required, audited). ### Booking eligibility (all enforced in the service; the server action, bulk booking and the job go through the same function)
Order is CONFIRMED/PROCESSING · COD or marketplace payment · not CANCELLED/REFUNDED/DELIVERED/FAILED_DELIVERY · not already BOOKED/BOOKING/MANUAL · recipient name, valid 11-digit BD mobile, and address present · **advance verified or waived, low-trust review done, fraud review done** (existing `assertDispatchReady`; a fraud approval never bypasses the advance: tested) · no unsourced units (procurement) · not marketplace-fulfilled · the provider has not confirmed a parcel already exists. The admin panel now lists **every** failing reason, not only the first (`computeBookingReadiness`), and shows what would be sent (recipient, phone, address, cash to collect) before the one-click booking.

### Booking state machine (`Order.courierBookingStatus`)
`NOT_BOOKED → BOOKING` (conditional claim before the network call; exactly one of N concurrent requests wins) `→ BOOKED` (response validated: id present, invoice echo must match) | `FAILED` (provider refused: 4xx) | `UNCERTAIN` (timeout / 5xx / unreadable / mismatched reply). `MANUAL` via manual entry (allowed from NOT_BOOKED/FAILED/UNCERTAIN, and re-editable while MANUAL). `create_order` is **never** retried automatically. An UNCERTAIN order is never re-booked blindly: a retry needs the admin's explicit confirmation AND, when lookup is enabled, the provider is asked first; if it positively confirms a parcel exists, `courierRemoteConfirmedAt` is set and re-booking is refused for good (enter details by hand or wait for the webhook, which adopts the consignment id). A stale `BOOKING` (>10 min) is converted to `UNCERTAIN` by the job. A booking failure touches only courier columns (tested: payments, stock and order status untouched).

### Shipment status mapping (Steadfast raw → event → order effect)
`in_review`, `pending`, `hold` → PENDING (none) · `delivered`, `delivered_approval_pending` → DELIVERED (walks order to DELIVERED through allowed transitions; **no payment**) · `partial_delivered*` → PARTIAL_DELIVERED (**no order change**; tracking-history line; attention list; COD flag) · `cancelled`, `cancelled_approval_pending` → CANCELLED (shipped order → FAILED_DELIVERY; otherwise flagged for an admin; never CANCELLED/REFUNDED, stock never moves) · `unknown*` / any new value → UNKNOWN (stored raw, no order effect). Changed from before: `cancelled` was labelled RETURNED (one existing assertion updated); `partial_delivered` used to complete the whole order. "Picked up / in transit / out for delivery / delivery failed" **cannot be derived** (not in the vocabulary) and are not simulated. Raw status is kept in `courierLastStatus` and in `CourierShipmentEvent`.

### Sync rules (webhook, poll and manual refresh share `applyCourierEvent`)
Idempotent (exact replay of a timestamped event is a no-op via a unique key); out-of-order safe (older provider time never overwrites newer; without a trusted time a lower-progress status never overrides a higher one; an unrecognised status may replace an in-progress one but never an approval-pending/final one); race safe (status claimed with a WHERE pinned to the state it was judged against, re-judged if someone moved first); a repeat of the recorded status re-checks the order so a crash between "recorded" and "order advanced" self-heals. A provider timestamp is trusted only if it carries a time zone and is not in the future. Every applied/ignored event is a row in `CourierShipmentEvent` (no customer data, no body); meaningful outcomes that do not move the order get a neutral line in the order tracking history.

### Webhook security
Not configured ⇒ 404. Missing/wrong/look-alike bearer ⇒ 401 (constant-time compare), nothing changes. 64 KB cap (bytes). Authenticated but malformed (not an object, no status, no id/invoice, oversize fields) ⇒ 400. Authenticated notice of another type ⇒ 200 "ignored". Consignment id and invoice that disagree ⇒ ignored (200) and logged. Unknown consignment ⇒ 200. **Limitation:** bearer-token auth only (no signature, so no replay-window beyond the idempotency/ordering rules). The token is a shared secret: rotate if exposed.

### COD reconciliation (extended, not replaced)
Source of truth unchanged: explicit `CourierCodEntry` rows and `Payment` records; nothing is overwritten. New: `Order.courierCodAmount` (what the courier holds for the consignment: booking echo / webhook `cod_amount`; **a consignment figure, never proof of collection**); flags `BOOKED_AMOUNT_MISMATCH`, `COLLECTION_UNCONFIRMED`, `PARTIAL_DELIVERY` beside the existing short/excess/missing/over-settled; derived remittance status (nothing due → awaiting confirmation → awaiting report → reported → partly settled → settled | discrepancy | resolved). Admin can **resolve** an open discrepancy (accept / write off) with a mandatory reason and the exact amount shown (refused if it changed since; append-only `CourierCodResolution`; audited as `COURIER_COD_RESOLVED`); a changed amount re-opens it. **Confirm cash collected** records the COD balance via the same `recordCodCollection` an admin "Delivered" uses; refused while a short collection/partial delivery is open or after a **written-off** shortfall (the full balance would overstate cash). Not automated: reading remittances from Steadfast (blocked, see above).

### Scheduled jobs (`GET|POST /api/courier/reconcile`, `Authorization: Bearer $CRON_SECRET`)
One pass: (1) stale `BOOKING` → `UNCERTAIN`; (2) UNCERTAIN → ask the courier (only if lookup enabled; records a positive answer only); (3) poll in-flight BOOKED consignments (CONFIRMED…OUT_FOR_DELIVERY; skips ones synced <5 min ago and settled ones), same path as the webhook; (4) only if `COURIER_AUTO_BOOK=true`, book CONFIRMED NOT_BOOKED orders through the full gate; (5) report delivered COD orders awaiting cash confirmation. Reliability: state lives in the DB; per-order lease `courierSyncLeaseUntil` (2 min; expires by itself; a failed poll sets a 15 min back-off), so overlapping runs and manual actions never process the same order at once; bounded batches (poll ≤100, book ≤50, recover ≤50); one order's error never stops the pass; re-running after a crash simply continues. **Recommended frequency: every 10–15 minutes** (a webhook is the primary channel; this is the safety net). Vercel Hobby allows only daily crons, so use an external scheduler (GitHub Actions / cron `curl -H "Authorization: Bearer $CRON_SECRET" https://…/api/courier/reconcile`). Daily is the minimum useful frequency; if only daily, stale/uncertain recovery is slow.

### 1. Provider-by-provider API verification (read this first)

Response per that README: `{ total_parcels, total_delivered, total_cancelled, total_fraud_reports: [] }`. Evidence = Steadfast's own published client package README (Packagist `steadfast-courier/steadfast-laravel-package` 2.0.0, author it.woop@steadfast.com.bd), which lists this endpoint among the official Postman collection's. The Postman page itself could not be opened. **Not documented/verified: error body shapes, rate limits, whether counts can be strings, what the fraud-report items contain, whether `total_parcels` includes in-progress parcels.** Steadfast reports no returned/failed counts, no rate, no score.
  **The previous adapter was wrong**: it called `/fraud_check/score/{phone}` and required `delivered_count` / `cancelled_count`, which do not match that documentation, so it could never have produced a result. It was deleted, with its two invented fixtures (`delivery_ratio`, `volume_band`, ...).

### 2. Architecture and data flow
`lib/courier-intelligence/` (pure): `types` (normalised `ProviderReport`: missing = `null`, never 0), `registry` (descriptors: capability, metrics, verification evidence, semantics), `steadfast-map` (strict mapper), `combine` (combined report), `trust` (evidence policy -> `assessTrust`).
`server/services/courier-intelligence.service.ts`: ONE service for every consumer. Flow per courier: unsupported -> `unsupported` (never called) -> disabled/not configured -> shared cache (newest stored row that has not expired and is not older than the caller's max age) -> in-flight dedupe -> DB-backed per-courier call budget -> adapter call with timeout -> typed result -> stored (`CourierIntelligenceSnapshot`) -> report. Never throws; a courier failing never discards another's answer. `courier-intelligence-admin.service.ts`: admin lookup (re-checks active admin, per-admin throttle, audit with masked phone only) and the order-page data (reads stored data only).
Consumers: **checkout** (`quoteAdvance` in `advance.service.ts`; asked for every order so fraud review has evidence; maxAge from the policy), **admin Fraud Check page** `/admin/fraud-check` (nav: Courier fraud check), **order page** (`OrderCourierIntelligence`), **fraud review** (customer lookup page shows the saved external report for every phone of the profile, beside the internal history), **manual recheck** (`recheckOrderFraud`).
Combined report rules (tested): only provider-reported counts; no-history = a real answer (zero); a provider without counts contributes nothing; percentage-only is shown separately and never counted; rate = delivered / (delivered + cancelled); returned/failed are shown but excluded from the denominator; parcels neither delivered nor cancelled are "not classified" and excluded; the figures say they are provider records, **not globally deduplicated** (no cross-courier parcel id); no counts => no rate, never a fabricated 50%.

### 3. Advance policy redesign (server-authoritative)
Removed: the default 50, the +/-10/20 formula, parcel-list aggregation. The input is the delivery success RATE (percent) from the combined report. States: `rated`, `no_history`, `insufficient` (too few parcels / couriers / evidence too old), `unavailable`, `invalid_phone`. Anything not `rated` is **unrated**: standard advance + staff review (when the review rule is on), exactly the conservative path a missing check always took. **An outage can never lower an advance** (tested with every reward switch on). Tiers compare the rate with the existing lines: below `lowBelow` (60) low (standard + review); at/above 60 standard; at/above `reducedFrom` (80) reduced; at/above `fullAt` (100) full (zero only with `zeroAtFullTrust`). New admin settings (Advance payment page, all validated, stored on `StoreSettings`): `minSample` (default 5 delivered+cancelled parcels: 1 of 1 is 100% but unrated), `minProviders` (1), `maxAgeSeconds` (3600), `rewardEnabled` (**default OFF**: a good record never lowers the advance until enabled), `creditUnverifiedPhone` (**default OFF**). **There is no phone verification in this project** (`isPhoneVerified()` is false and a profile phone is free text), so positive evidence counts only if the admin turns BOTH switches on, accepting that a customer can type someone else's number. Negative evidence always counts. Website order history is never used. The customer cannot supply a rate, tier or amount (tested with hostile input). Each order stores `trustSnapshot.courier` (frozen per-courier evidence + policy used) and a compact `fraudCheck` summary; `trustScore` now holds the rate rounded to an integer, or null (unrated). Old orders keep their old-model values (labelled "older points model" in the panel).

### 4. Cache, persistence, reliability, privacy
Table `CourierIntelligenceSnapshot` (append-only history that doubles as the cross-instance cache; no Redis exists in this project). Stores: keyed HMAC hash of the phone (`AUTH_SECRET`), masked phone, courier, status/reason code, counts, fraud-report COUNT, source, timestamps. **No raw phone, no raw provider payload, no credentials, no fraud-report contents.** Cache time = `FRAUD_CHECK_CACHE_SECONDS` (default 600; 0 = off but history is still kept); failures are remembered for at most 30 s; a manual refresh always asks again and ADDS a row (earlier results preserved); budget per courier per minute in the database (`FRAUD_CHECK_MAX_CALLS_PER_MINUTE`, default 60; refusals become `rate_limited`, not stored); admin lookups throttled to 90/hour per admin; simultaneous lookups of one phone on one instance share one call (across instances the cache + budget bound the load). The lookup is read-only and is **not retried** (protects checkout latency and quota; an admin can recheck). Timeouts: `FRAUD_CHECK_TIMEOUT_MS` (500-10000, default 3000) with a second guard. Retention: rows older than `COURIER_INTEL_RETENTION_DAYS` (default 90) are deleted by the existing `/api/courier/reconcile` job. Logs carry provider, reason code and the MASKED phone only (tested: no full phone and no credential in any log, row, audit event or status output). Provider messages are never shown: only reason codes mapped to fixed text.

### 10. Known limitations
- Steadfast's contract is unverified against the live API (see section 1); until the first real call, expect `invalid_response` if it differs, which safely means "unrated".
- Counts are provider records and cannot be deduplicated across couriers; with Steadfast alone there is no cross-courier question.
- Steadfast's cancelled outcome is not distinguishable into returned / refused / failed.
- No phone verification exists, so by default (and by design) a good courier record never lowers an advance. Turning rewards on with unverified phones lets a customer borrow someone else's number.
- The in-flight dedupe is per server instance; across instances duplicates are bounded by the cache and budget, not eliminated.

## P7.3.3 — E-mail queue foundation (implemented; unit/service tests pass; NOT run against Postgres, a real SMTP server, `prisma generate` or `next build`)

**Audit result (what existed):** no generic queue/worker (the "job" code in `features/admin/job-manager.tsx` is job *postings*). The project's established background pattern is a PostgreSQL table with a unique key + conditional-UPDATE claim + backoff + stale-claim recovery (`TrackingEventLog`), drained by an **external scheduler** calling a route with `Authorization: Bearer $CRON_SECRET` (`/api/tracking/retry`, `/api/courier/reconcile`, `/api/checkout-recovery/cleanup`), with `after()` as a best-effort accelerator. Rate limiting is PostgreSQL too (`RateLimitBucket`). **Decision:** follow that pattern with one new table (`EmailJob`); Redis/BullMQ/pg-boss were not justified (single small store, no worker host, volume capped by Gmail's own limits) and were not added.

- **Model** (additive migration `20261128000000_email_queue_p733`, rollback in the file): `EmailJob` (+ enum `PENDING|PROCESSING|SENT|FAILED`). Unique `dedupeKey`; `priority` (0 individual, 1 bulk); `attempts`, `nextAttemptAt`, `lockedAt`, `sentAt`, fixed `errorCode`/`errorMessage`, `messageId`. Written by hand: run `prisma generate` and confirm `prisma migrate diff` shows no drift.
- **API (server only, `src/server/services/email-queue.service.ts`):** `enqueueEmail(input, {priority?, kick?})` one e-mail, never throws; `enqueueEmails(list)` bulk (inserts in chunks of 500, returns at once, reports invalid entries by index, safe to repeat); `deliverEmailJob(id)`; `processEmailQueue()`. Input = `{ kind, dedupeParts[], to, subject, text, html? }`. Everything must send through this queue or `sendSmtpMail()`; nothing else may create a transport.
- **Duplicates:** `dedupeKey = kind:sha256(kind + parts)` (parts trimmed/lower-cased; no address in the key). Pick parts that identify the *logical* e-mail, e.g. `("order-confirmation", [orderNumber])`, `("campaign", [campaignId, recipient])`. Re-queueing returns the existing job (`created:false`) even after it was SENT.
- **Not blocking:** enqueue = database inserts only. A single e-mail adds an `after()` kick (skipped when SMTP is not ready); bulk never kicks. The guaranteed sender is the worker: `POST /api/email/queue` (Bearer `CRON_SECRET`, `maxDuration 60`, 45 s internal time limit). **Schedule it every 1-5 minutes** (Vercel Hobby = daily only: use an external scheduler). Until then single e-mails still go out through the `after()` kick, bulk waits.
- **Retry:** failure classes in `queue-policy.ts`. *Permanent* (`recipient_rejected`) -> FAILED at once. *Temporary* (timeout, connection, DNS, `send_rejected`, unknown) -> PENDING with backoff 1 min / 5 min / 30 min / 2 h, FAILED after 5 attempts. *Systemic* (`auth_failed`, `tls_failed`, `invalid_config`, `not_configured`, `dependency_missing`) -> job goes back to PENDING **without using an attempt**, waits 30 min, and the run stops (no hammering of Gmail). If SMTP is not ready at all, the run touches nothing. Queued > 7 days -> FAILED `expired`, body removed. A claim stuck in PROCESSING > 5 min is re-claimed; one with no attempts left is FAILED `attempts_exhausted`.
- **Rate limits:** per run `EMAIL_QUEUE_BATCH_SIZE` (20), rolling hour `EMAIL_QUEUE_MAX_PER_HOUR` (100), rolling day `EMAIL_QUEUE_MAX_PER_DAY` (400), counted from `SENT` rows (database-backed, fails closed; not `RateLimitBucket`, which fails open by design). Individual e-mails drain before bulk. Defaults are below Gmail's ~500/day (free account); raise them only if the sending account allows it. Concurrent runs can overshoot the hour/day figure by at most one batch.
- **Privacy/logging:** the row holds the recipient and body until sent. Body is cleared on SENT and on `expired`; kept on other FAILED rows for a future manual retry. SENT rows are purged after 30 days, FAILED after 60. Logs (`logServerWarning/Info`) and stored errors contain only job id, kind, fixed code, attempt number; never an address, subject, body, password or raw server reply (tests assert this).
- **At-least-once:** if a worker dies after the SMTP server accepted a message but before the row is marked SENT, the stale claim is retried and the recipient may get it twice. SMTP cannot prevent this; the window is one database write.
- **Tests:** `tests/unit/email-queue-policy.test.ts` (8), `tests/services/email-queue.test.ts` (29: lifecycle, after() kick and its failure, duplicates incl. concurrency, bulk, rate limits, retry/give-up, permanent, systemic pause, claim exclusivity, overlapping runs, crash recovery, housekeeping, log safety, route auth). Five deliberate code mutations (stale claim, attempt refund, dedupe, budget, body scrub) were each caught. Full `tests/unit` + `tests/services`: 1144 run, 1112 pass, **26 fail, the identical 26 as on the untouched P7.3.2 ZIP** (missing packages/assets in this sandbox: bcryptjs, public brand assets, real zod 4, etc.). Run here with a global `tsx` and a zod 3.25 stand-in (`TEST_ZOD_PATH`).
- **Unverified (be explicit):** real PostgreSQL (migration, the conditional-UPDATE claim under true concurrency: the fake DB serialises, so exclusivity is by construction of the single UPDATE, not proven by tests), `prisma generate`/`tsc` with real Prisma types (a scoped `tsc` showed only the usual missing `next`/`@types/node`), `next build`/ESLint, a real Gmail send (still never run), the scheduler.
